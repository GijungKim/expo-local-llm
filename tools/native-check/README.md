# Native compile checks

The `Native compile` workflow regenerates the Expo SDK 58 example app and
compiles its development configuration on both platforms. It runs on every
push to `main` and on pull requests that change anything other than Markdown,
`docs/` or `LICENSE`. The filter is a job inside the workflow rather than a
workflow-level path filter, so a docs-only pull request reports the native
jobs as skipped (which counts as passing) and the workflow can still be
configured as a required check.

## Toolchain contract

- Bun 1.4.2; the repository and example installs are locked by their respective
  `bun.lock` files and use `--frozen-lockfile`.
- Node.js 24 (Expo SDK 58 requires Node.js 22.13+, 24.3+ or 26+).
- Android: Temurin JDK 25, minimum SDK 26, compile SDK 37, target SDK 36, build-tools 37.0.0,
  NDK 27.1.12297006, Kotlin 2.3.0+, and the Gradle wrapper generated by Expo prebuild.
  The example configures Kotlin 2.3.0 through `expo-build-properties`; ML Kit beta5 / Schema alpha2
  also require the coroutines 1.11 ABI supplied by the library. JDK 24+
  restricts native access (JEP 472), so `android.sh` passes
  `--enable-native-access=ALL-UNNAMED` to the Gradle JVM.
- iOS: the GitHub-hosted `macos-26` image with Xcode 26.4.1, CocoaPods from
  that runner image, and an iOS 16.4 deployment target.
- Xcode 26.4.1 is the compatibility floor for the Apple code. A newer SDK can
  annotate an API as available on an older OS while the older SDK never
  declares it, so build against the floor instead of trusting the annotation.

GitHub's authoritative [`macos-26` runner manifest][macos-26-manifest] lists
Xcode 26.4.1 at `/Applications/Xcode_26.4.1.app`, which is the path selected by
the workflow.

The generated CocoaPods graph is resolved after clean prebuild because the
project does not maintain an SDK 58 `Podfile.lock`. JavaScript package
resolution is reproducible through the two committed Bun lockfiles.

## What the checks establish

`android.sh` runs `:app:assembleDebug`, compiling all autolinked native modules
and packaging a development APK. It also requires Gradle to expose the
`:expo-local-llm` project, execute its Kotlin compilation task, and produce JVM
unit test results. `ios.sh` performs a signing-disabled Debug build for a generic
iOS Simulator destination, compiling and linking the Swift module against the
Xcode 26 SDK.

The Android JVM tests cover library logic that does not need the model runtime —
prompt assembly, conversation trimming, image input validation, bitmap decoding,
and bitmap ownership when cancellation races decoding or a paused SDK worker.
Image tests use Robolectric; they do not establish image understanding or
inference behavior on an AICore-capable device. Gradle reports a task with no
matching sources as `NO-SOURCE` and still passes, so the check asserts that test
result files exist instead of trusting the task outcome.

The example does not install the package. Autolinking finds it through
`expo.autolinking.nativeModulesDir: ".."` in `example/package.json`, so Gradle
and CocoaPods compile the repository's own `android/` and `ios/` sources, and
Metro resolves the JavaScript from the repository root (`example/metro.config.js`).
This is the layout `create-expo-module` generates. An earlier `file:..`
dependency made Bun copy the whole repository, including `node_modules` and the
example itself, into the example on every install.

Preparation validates Expo's resolved module metadata on both platforms. The
iOS check additionally requires the pod lock, generated `ExpoModulesProvider`,
and Pods project to contain `ExpoLocalLlm` and register
`ExpoLocalLlmModule`. After compilation, the iOS check requires build output
from the `ExpoLocalLlm` pod target rather than accepting a host-only app build.

Neither check runs model inference. In particular, a successful Simulator
build does **not** establish Foundation Models availability or behavior on a
supported physical Apple Intelligence device. The Android build also requires
every declared Maven dependency to resolve successfully; dependency resolution
failures are hard CI failures.

## Local use

From the repository root:

```sh
tools/native-check/prepare-example.sh android
tools/native-check/android.sh

tools/native-check/prepare-example.sh ios
tools/native-check/ios.sh
```

These commands delete and regenerate the selected `example/android` or
`example/ios` directory. Run them in a clean checkout or disposable worktree
if you need to preserve checked-in generated files. Local Android setup must
provide `ANDROID_HOME`/`ANDROID_SDK_ROOT` with the SDK packages listed above.
Local iOS setup must select Xcode 26.4 or newer and have CocoaPods available.

[macos-26-manifest]: https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md

### Android tool-calling compiler floor

The library remains compile SDK 35 / min SDK 26; the SDK 58 example uses compile SDK 37. The example pins Kotlin 2.3.0. A focused real compile against `genai-prompt:1.0.0-beta5`, `genai-common:1.0.0-beta5`, `genai-schema:1.0.0-alpha2`, and their Kotlin stdlib 2.4.0 dependency passed with compiler 2.3.0 and failed with 2.2.21 (incompatible 2.4 metadata). No metadata-skip flags were used. The probe constructs runtime schemas, declarations, calls, responses with nullable SDK IDs, role-tagged content, and a request using `setTools`. The full library and JVM tests also use 2.3.0. This is the tested floor; published artifact metadata alone does not mean the compiler must be 2.4.

For an existing generated checkout, do not clean prebuild to validate a local change. Keep `example/android/gradle.properties`'s `android.kotlinVersion` consistent with `example/app.json`, then run from `example/android`:

```sh
./gradlew :app:createBundleReleaseJsAndAssets --rerun \
  :expo-local-llm:compileDebugKotlin :expo-local-llm:testDebugUnitTest \
  :app:assembleDebug :app:assembleRelease -PreactNativeArchitectures=arm64-v8a \
  -Pandroid.enableMinifyInReleaseBuilds=true --no-daemon --console=plain
```

Forcing the Release bundle task matters in an existing checkout: Gradle can otherwise reuse a bundle after library sources outside `example/` change. This packages Debug and R8-minified Release APKs without installing or launching them. Local validation can use JDK 17. Tool tests exercise the production declaration/batch validators, pending-call store, generation ownership, callback filtering, result protocol, history trimming, and bitmap ownership. They do not simulate AICore inference.

SDK artifact limitations observed on JDK 17: beta5 advertises Kotlin default-argument `FunctionCall.copy` metadata without shipping `copy$default`, so tests use its public constructor (as production does). Instantiating SDK `ImagePart` on the JVM raises a verifier error in its URI constructor. The image tests exercise our actual decoding, ownership and bitmap-free transcript records, without bypassing JVM verification or replacing SDK classes. DEX packaging and Android hardware image inference are separate checks.

These are helper tests, not `LLMSession` integration tests. Actual multi-round orchestration, model-close ownership, callback/return accumulation, registration transitions, and image retention through SDK requests remain unverified. In particular, the image-history test does not construct an image-bearing tool request.
