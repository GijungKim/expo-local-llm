# Native compile checks

The `Native compile` workflow regenerates the Expo SDK 57 example app and
compiles its development configuration on both platforms. It runs on every
pull request to `main` (rather than using workflow-level path filters), so it
can safely be configured as a required check.

## Toolchain contract

- Bun 1.4.2; the repository and example installs are locked by their respective
  `bun.lock` files and use `--frozen-lockfile`.
- Node.js 24 (Expo SDK 57 requires Node.js 22.13 or newer).
- Android: Temurin JDK 17, minimum SDK 26, compile/target SDK 36, build-tools 36.0.0,
  NDK 27.1.12297006, and the Gradle wrapper generated by Expo prebuild.
- iOS: the GitHub-hosted `macos-26` image with Xcode 26.4.1, CocoaPods from
  that runner image, and an iOS 16.4 deployment target.
- Xcode 26.4.1 is the compatibility floor for the Apple code. A newer SDK can
  annotate an API as available on an older OS while the older SDK never
  declares it, so build against the floor instead of trusting the annotation.

GitHub's authoritative [`macos-26` runner manifest][macos-26-manifest] lists
Xcode 26.4.1 at `/Applications/Xcode_26.4.1.app`, which is the path selected by
the workflow.

The generated CocoaPods graph is resolved after clean prebuild because the
project does not maintain an SDK 57 `Podfile.lock`. JavaScript package
resolution is reproducible through the two committed Bun lockfiles.

## What the checks establish

`android.sh` runs `:app:assembleDebug`, compiling all autolinked native modules
and packaging a development APK. It also requires Gradle to expose the
`:expo-local-llm` project and execute its Kotlin compilation task. `ios.sh`
performs a signing-disabled Debug build for a generic iOS Simulator destination,
compiling and linking the Swift module against the Xcode 26 SDK.

Preparation validates Expo's resolved module metadata on both platforms. The
iOS check additionally requires the pod lock, generated `ExpoModulesProvider`,
and Pods project to contain `ExpoLocalLlm` and register
`ExpoLocalLlmModule`. After compilation, the iOS check requires build output
from the `ExpoLocalLlm` pod target rather than accepting a host-only app build.

Neither check runs model inference. In particular, a successful Simulator
build does **not** establish Foundation Models availability or behavior on a
supported physical Apple Intelligence device. The Android build also requires
every declared Maven dependency to resolve successfully; dependency resolution
failures are hard CI failures.

## Local use

From the repository root:

```sh
tools/native-check/prepare-example.sh android
tools/native-check/android.sh

tools/native-check/prepare-example.sh ios
tools/native-check/ios.sh
```

These commands delete and regenerate the selected `example/android` or
`example/ios` directory. Run them in a clean checkout or disposable worktree
if you need to preserve checked-in generated files. Local Android setup must
provide `ANDROID_HOME`/`ANDROID_SDK_ROOT` with the SDK packages listed above.
Local iOS setup must select Xcode 26.4 or newer and have CocoaPods available.
